## 3. What Dexo does that none of them do

1. **Write access as an out-of-process, one-use, time-boxed grant.** No server in this group has grants. Their write controls are a startup switch (postgres-mcp `--access-mode`, mysql `ALLOW_*`, dbhub `readonly`, supabase `read_only`). dbhub's own code names "confirm" as a future extension point (`src/utils/sql-access-policy.ts:41`). Dexo's grant is bound to one connection, a selector and a tool, expires in at most 24 h, and the MCP process can neither create nor list it.
2. **Human approval of each write in a separate trusted UI.** Dexo's `--ask` grants wait in the TUI's Agent Activity screen. The person approves with a second confirmation, the request is withdrawn if the agent cancels, and revoking a grant denies its pending requests. The nearest feature is supabase's in-client elicitation, which only covers destructive SQL and is shown by the same client that runs the agent.
3. **Production can never be written over MCP**, with or without a grant, and an unknown environment label counts as production. None of the five has any notion of environments.
4. **Object allow/deny rules enforced on raw SQL.** Every relation in a statement is resolved and checked, and deny always wins. The others either have no object rules (dbhub, postgres-mcp, toolbox outside BigQuery datasets) or only per-schema write switches (mysql).
5. **A durable audit trail that stores no SQL.** Each call records decision, status, rows, bytes and object, with retention and a live view. The best of the rest is dbhub's 100 in-memory traces, and toolbox has OTel infrastructure tracing.
6. **Idempotent writes** (`operation_id`): a retry returns the first result. Nobody else has this.
7. **Notes as business semantics for agents.** Per-table and per-column notes are stored per connection, fall back to `COMMENT`, are returned by `object_describe`, and are searchable by `catalog_search` without exposing hidden objects. postgres-mcp users are still asking for plain comments (#71, 3 👍).
8. **Stricter read guard than the closest rival.** The statement must parse as exactly one read; data-modifying CTEs, `SELECT … INTO`, locking clauses and side-effecting functions are refused before `BEGIN READ ONLY`. dbhub's open bug #448 is `set_config()` inside a SELECT clearing the statement timeout, and Dexo's guard already refuses `set_config` (`crates/dexo-sql/src/statement_guard.rs:93`). toolbox's prebuilt `get_query_plan` templates raw SQL into `EXPLAIN` and warns about injection itself.
9. **Row and byte limits with explicit truncation and paging on every read path.** postgres-mcp, supabase and toolbox have no row cap at all. mysql documents a timeout and rate limit that its source never reads.
10. **Setup and diagnosis built into the binary.** `mcp setup` edits four clients' configs with backups and a dry run, and `mcp doctor --probe` starts the server and lists its tools the way a client would. The most-upvoted issues in three of the five trackers are "can't connect / server disconnected / silent exit" (mysql #79 12 👍, #74, #108; supabase #20, #49, #133; postgres-mcp #65, #91, #95). Shipping one static binary also avoids the npx/uvx/Docker startup failures behind those issues.
11. **The agent's server and the human's workbench share one policy engine.** The same read-only, confirm-destructive and production rules apply in the TUI, the CLI and MCP, and the person reviewing the agent's work is in the same terminal tool. dbhub's web workbench is the only comparable feature, and it is a browser page with no approvals.
12. **The tool list follows the grants.** Write tools appear only while a grant is active and disappear when it is revoked. toolbox and supabase prune write tools, but only from a static read-only flag.
13. **DuckDB, with CSV/Parquet/JSON files as tables.** No one in the group has it, and toolbox has an open request for it (#2077).

Positioning line this supports: *"The other database MCP servers give your agent a connection. Dexo gives it a permission: scoped, time-boxed, approved by you, and logged."*

## 5. Top 5 recommendations (ranked by value/effort)

1. **Cut result size and fence untrusted data (S).** Lower the default `max_bytes` from 1 MiB, check that clients are not given both the Markdown and the `structuredContent` copy, and wrap returned rows in a per-call `untrusted-data` fence like supabase's. This costs a few lines in `render.rs`/`profile.rs`, directly supports the guardrails pitch, and answers dbhub's "token conscious" claim.
2. **Performance triage tools (S–M):** a top-queries tool (`pg_stat_statements`; MySQL statement digests), a locks and long-running-transaction tool, and a health summary, all read-only and listed only with `--allow-tool`. Together with the existing `query_explain` + hypothetical indexes, this covers postgres-mcp's whole pitch with Dexo's guards around it. Optionally add opt-in `analyze: true` on reads inside the read-only transaction with rollback, never on production.
3. **Saved queries as MCP tools (M).** Expose a profile's named saved queries, with their parameters, as typed tools that still go through selectors, limits and audit. This gives a `query-mode none` profile something useful to do, and it is the flagship feature of both dbhub (custom tools) and toolbox (tools.yaml), built from data Dexo already stores.
4. **Column-level deny, then masking (M).** Allow 4-segment selectors (`db.schema.table.column`). Refuse any statement that references a denied column, refuse `*` on tables that have one, and drop denied columns from `object_describe`/`data_read`. Optional value masking for data a profile may see but not read in clear can come later. This is the one guardrail that rivals market and Dexo lacks (mysql PII mode, the Bytebase upsell, postgres-mcp #167).
5. **Get listed (S):** publish a `server.json` to the MCP Registry and ship a Claude Code plugin/marketplace entry that runs `dexo mcp setup`. Each rival is discovered through a registry or store, and Dexo's setup and doctor already solve the top complaint in their trackers. Lead the launch copy with the grants and approval story from section 4.

Not recommended for now: an HTTP transport (keep "no network listener" as a stated safety position), Supabase-style branching (vendor-specific), a full workload index advisor (L; the hypopg loop covers most of it).
Honorable mentions: connection `description` in `list_connections` (S); an MCP tool to take a schema snapshot and diff it against the live database, for the generate→apply→verify loop (M).
